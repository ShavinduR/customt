# CustomT Security and Privacy Assessment: Phase 5 and KYB readiness

**Scope:** `main` at `0e16cea` (pull requests #4 and #5: security hardening, Global Feed, micro-storefronts, Direct RFQs), plus the **KYB onboarding proposal** (`docs/KYB_ARCHITECTURE_PROPOSAL.md`).
**Method:** manual review of every route, service and model that handles posts, uploads, storefronts, roles and PII; review of the React code paths that render user content; targeted tests.

> **Important:** KYB onboarding is **not implemented yet**. `main` has no NIC, BR or utility-bill fields, no `PENDING_APPROVAL` state and no Cloudflare R2 integration. Those parts of this report are therefore **requirements and reference designs** for the KYB build, not findings in deployed code. Everything else was tested against the real code.

## 1. Findings fixed in this round

### 1.1 Cross-user file reuse in posts and covers (Medium, IDOR-like)

**Problem.** Post photos and the storefront cover were validated only as "a file uploaded to CustomT". Vendors can see buyers' design images (the URLs are in RFQ specs), so a vendor could post a buyer's **unreleased logo or artwork** on the public Global Feed, or use another vendor's product photos as their own.

**Fix.** Every upload's filename already starts with the uploader's user id (`<userId>-<timestamp>-<random>.<ext>`, generated by the server). The validator now checks that prefix:

```js
// backend/utils/uploadUrl.js
const UPLOAD_PATH = /^\/uploads\/logos\/([a-f0-9]{24})-\d{10,16}-[a-f0-9]{8}\.(png|jpg|webp|svg)$/;

function isUploadedFileUrl(raw, { ownerId, rasterOnly = false } = {}) {
  ...
  const match = UPLOAD_PATH.exec(pathname);
  if (!match) return false;
  if (ownerId && match[1] !== String(ownerId)) return false;   // must be the caller's own upload
  if (rasterOnly && !RASTER.has(match[2])) return false;        // no SVG in public content
  return true;
}
```

```js
// backend/models/Post.js: photos must belong to the posting vendor
validator(list) {
  return (list || []).every((url) => isUploadedFileUrl(url, { ownerId: this.vendorId, rasterOnly: true }));
},
```

The same rule applies to the storefront cover (`User.storefront.coverUrl` and `feedService.updateStorefront`) and to dispute evidence (it must be the buyer's own uploads).

### 1.2 Upload quota (Medium, resource exhaustion)

```js
// backend/routes/uploadRoutes.js
const uploadQuota = rateLimit({
  windowMs: 60 * 60 * 1000,
  limit: 40,                                   // per user per hour
  keyGenerator: (req) => String(req.user._id),
  message: { success: false, code: 'UPLOAD_QUOTA', message: 'Upload limit reached (40 files per hour). Please try again later.' },
});
router.post('/logo', protect, authorize(ROLES.BUYER, ROLES.VENDOR, ROLES.ADMIN), uploadQuota, ...);
```

40 files an hour covers real use: a design with 8 images plus several 6-photo posts.

### 1.3 Raster-only public images (Low)

SVGs were already harmless: they are rendered through `<img>`, which never runs scripts, and served with `Content-Security-Policy: sandbox` and `nosniff`. Still, there is no reason for vector files in a photo feed, so feed photos and covers are now PNG, JPG or WEBP only.

## 2. OWASP review: XSS (A03 Injection)

**Result: no exploitable XSS in the Global Feed, storefront or composer.**

| Vector | Why it is safe |
|---|---|
| `title`, `postDescription`, `composition`, `bio` | Rendered as React text children (`{post.postDescription}`). React escapes `<`, `>`, `&` and quotes. Verified in Chromium: a description `<img src=x onerror=…><script>…</script>` and a title `<b onmouseover=…>` rendered as literal text; no element was injected and no script ran. |
| HTML injection APIs | None: `dangerouslySetInnerHTML`, `innerHTML`, `eval` and `new Function` don't appear anywhere in `frontend/src`. |
| Image `src` | Only server-validated upload paths (section 1.1), so `javascript:` and `data:` URLs are impossible. |
| Links | Storefront links are built from server ObjectIds; call-to-action links use `URLSearchParams` (encoded). |
| Query string prefill (`/create-rfq?garment=…`) | Applied only if the value is in the server catalogue's whitelist; `vendorId` must match `^[a-f0-9]{24}$`. |
| Server storage | Text is stored **unencoded** and encoded at output time. That is the correct pattern (HTML-encoding on input corrupts data and gives false confidence). |
| Defence in depth | Strict CSP on the frontend from #4 (`script-src 'self' 'wasm-unsafe-eval'`, no inline scripts), so even an injected `<script>` would not run. |
| E-mails | The password-reset template escapes the user's name and link (`escapeHtml`). |

**Legacy note.** RFQs created *before* #4 could hold external `http(s)` image URLs (never `javascript:`, which the old rule rejected). `SpecSummary` renders them as links with `rel="noreferrer"`. This is low risk; a one-off cleanup query can remove them if wanted.

## 3. OWASP review: IDOR (A01 Broken Access Control)

**Result: confirmed secure.** Every endpoint resolves ownership on the server from `req.user`. Ids taken from the URL are only used to look the object up, then checked.

| Endpoint | Check |
|---|---|
| `DELETE /api/posts/:id` | Post owner or admin only, otherwise 403 (end-to-end test: another vendor gets 403) |
| `GET /api/posts/:id` | Archived posts, or posts by unverified vendors, are 404 except for the owner or an admin |
| `POST /api/posts` | `vendorId` always comes from `req.user`; `postInput()` never copies `vendorId`, `status` or `contactFlags` from the body |
| `GET /api/vendors/:id/storefront` | Non-vendors and unverified vendors are 404; no phone, e-mail or business registration number in the response |
| `PATCH /api/vendor/storefront` | Acts on `req.user` only; there is no id in the URL |
| Direct RFQ | `directVendorId` is `immutable`; other vendors get 403 on view and bid (end-to-end tested) |
| Orders and chat (from #4) | `loadOrderForUser` and `loadChatOrder` check that the caller is a party (or admin, read-only) |
| Admin routes | `router.use(protect, authorize('admin'))` on the whole router |

**Requirements for the KYB endpoints**, so they stay IDOR-free when built:
1. Applicant routes (`/api/kyb/application…`) take **no application id**. They always load `VendorApplication.findOne({ userId: req.user._id })`.
2. Admin document routes check that the document belongs to the application: `application.documents.id(docId)`, never `KybDocument.findById(docId)` on its own.
3. Never accept `storageKey`, `status`, `decision` or `userId` from a request body. Copy only allowed fields, as `postInput()` does.
4. End-to-end tests: buyer A requests buyer B's application, giving 404; a non-admin requests a document, giving 403; a document id from another application, giving 404.

## 4. Role and state manipulation

**Result today: no bypass.** Postman attempts tried against the code:

| Attempt | Result |
|---|---|
| `POST /auth/register {"role":"admin"}` | 400, only buyer or vendor allowed (end-to-end tested) |
| `POST /auth/register {"role":"vendor","isVerified":true}` | Account created with `isVerified: false`; the body flag is ignored |
| `PATCH /auth/me {"role":"vendor","isVerified":true,"trustScore":5}` | Ignored: only `name`, `phone` and the vendor profile fields are copied, never the whole body |
| Vendor raises capacity, adds a capability or renames the company | `isVerified` resets to false and needs admin re-verification |
| Forged JWT with `role: admin` | Rejected: HS256 is pinned, and the role is read from MongoDB on every request (`protect`), not from the token |
| `PATCH /admin/vendors/:id/verification` as a vendor | 403 (admin router) |
| Admin verifies a *buyer* id | 404: the query requires `role: 'vendor'` |
| Verification with an expired licence | 400 |

**Requirements for `PENDING_APPROVAL` when KYB is built:**
1. **One** server function performs all application status changes, using a transition table:
   ```js
   const TRANSITIONS = {
     DRAFT: ['PENDING_APPROVAL', 'WITHDRAWN'],
     PENDING_APPROVAL: ['APPROVED', 'CHANGES_REQUESTED', 'REJECTED', 'WITHDRAWN'],
     CHANGES_REQUESTED: ['PENDING_APPROVAL', 'WITHDRAWN'],
   };
   const ACTOR = { PENDING_APPROVAL: 'applicant', WITHDRAWN: 'applicant', APPROVED: 'admin', CHANGES_REQUESTED: 'admin', REJECTED: 'admin' };
   ```
   Any other `from → to`, or the wrong actor, gives 409 or 403.
2. `role`, `vendorStatus` and `isVerified` are **never** copied from a request body anywhere. Only the admin decision service sets them.
3. Approval re-checks the evidence server-side: every document `ACCEPTED`, all required types present, BR number unique. The admin UI's checklist is not trusted.
4. Approval uses **optimistic concurrency** (as orders do now), so two admins can't make conflicting decisions.
5. After approval, disconnect the user's sockets (as is already done on a password change) so the role-room membership refreshes.

## 5. Data privacy (PII)

### 5.1 Current state

| Data | Storage | Exposure |
|---|---|---|
| Passwords | bcrypt, cost 12 | Never returned |
| O2O PIN | AES-256-GCM (from #4) | Buyer only |
| Phone, e-mail | Plain text (needed for login, notices, the self-dealing check) | Owner and admins only; stripped from the counterpart's view and from feed and storefront responses |
| Unfiltered chat text (`originalBody`) | `select: false` | Admins only |
| NIC, BR copy, utility bill, invoices | **Not collected yet** | none |
| Atlas | Encrypted at rest by the provider; TLS in transit | none |

### 5.2 NIC handling (requirement for KYB)

The NIC must be **searchable for duplicates** (one person, many vendor accounts) but **never readable** from the database:

```js
// Keyed hash, NOT bcrypt (bcrypt is salted, so it can't find duplicates) and NOT a bare SHA-256
// (only ~10^12 possible NICs, so a plain hash is brute-forceable in hours).
const crypto = require('crypto');
function nicFingerprint(nic) {
  const normalised = String(nic).toUpperCase().replace(/[^0-9VX]/g, '');   // 9 digits + V/X, or 12 digits
  return crypto.createHmac('sha256', process.env.KYB_HASH_KEY).update(normalised).digest('hex');
}
// Stored: { nicHash: nicFingerprint(nic), nicLast4: normalised.slice(-4) }, never the full NIC.
```

- `KYB_HASH_KEY`: 32 random bytes, stored only in Render's environment, **separate** from `JWT_SECRET`.
- The NIC *image* is in private R2 storage (section 6); the database holds only the hash and the last 4 characters for the reviewer to compare.
- Business registration numbers are company data, not personal data: stored in plain text with a unique index.

### 5.3 Sri Lanka Personal Data Protection Act No. 9 of 2022: gaps to close with KYB

1. **Purpose and consent:** a privacy notice on the KYB form, and `consentAt` stored (already in the proposal).
2. **Data minimisation:** collect only what verification needs; strip EXIF/GPS from photos (re-encode with `sharp`).
3. **Retention:** delete rejected applicants' documents after a fixed period (proposed 180 days, enforced with an R2 lifecycle rule plus a scheduled job); approved vendors' documents for as long as the account is active plus a defined period.
4. **Rights of the person:** add `GET /api/auth/me/data` (export) and an account-deletion route that anonymises the user and deletes their KYB objects while keeping financial ledger entries, which must be retained.
5. **Access accountability:** a `KybAccessLog` entry for every document view.
6. **Breach readiness:** document who is notified and how. Logs must never contain document contents, NICs or tokens (`morgan` logs only method, URL and status).

## 6. Cloudflare R2 configuration for KYB documents (reference design)

### 6.1 Bucket and credentials (Cloudflare dashboard)

1. **R2 → Create bucket** `customt-kyb`. Choose a location hint near your users (for example *Asia-Pacific*).
2. **Public access stays off:**
   - do **not** enable the `r2.dev` public URL;
   - do **not** connect a custom domain;
   - **no CORS policy** (the browser never talks to R2 directly).
3. **R2 → Manage API tokens → Create API token:**
   - permission **Object Read & Write**;
   - **apply to the `customt-kyb` bucket only** (not "all buckets");
   - optionally restrict client IPs.

   Copy the Access Key ID and Secret Access Key **once**, into Render's environment settings:
   ```
   KYB_S3_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
   KYB_S3_BUCKET=customt-kyb
   KYB_S3_ACCESS_KEY_ID=…        (Render secret, never in Git)
   KYB_S3_SECRET_ACCESS_KEY=…    (Render secret, never in Git)
   KYB_HASH_KEY=…                (32 random bytes, hex)
   ```
4. **Object lifecycle rule:** delete objects under `kyb/rejected/` after 180 days. The application service moves (copies, then deletes) a rejected application's objects there.
5. R2 encrypts every object at rest automatically, so no setting is needed.

### 6.2 Storage module (`backend/services/kybStorage.js`, to add with KYB)

```js
const crypto = require('crypto');
const { S3Client, PutObjectCommand, GetObjectCommand, DeleteObjectCommand } = require('@aws-sdk/client-s3');
const { getSignedUrl } = require('@aws-sdk/s3-request-presigner');

const s3 = new S3Client({
  region: 'auto',                                   // required value for R2
  endpoint: process.env.KYB_S3_ENDPOINT,
  credentials: { accessKeyId: process.env.KYB_S3_ACCESS_KEY_ID, secretAccessKey: process.env.KYB_S3_SECRET_ACCESS_KEY },
});
const BUCKET = process.env.KYB_S3_BUCKET;
const SIGNED_URL_SECONDS = 60;

/** Key is built ONLY from server-side values; the user's filename never reaches the path. */
function objectKey({ userId, applicationId, type, ext }) {
  return `kyb/${userId}/${applicationId}/${type}/${crypto.randomUUID()}.${ext}`;
}

async function putDocument({ key, body, contentType }) {
  await s3.send(new PutObjectCommand({
    Bucket: BUCKET,
    Key: key,
    Body: body,                                     // Buffer from multer.memoryStorage(), already type-checked
    ContentType: contentType,                       // the verified type, not the browser's claim
    ContentDisposition: 'attachment',
    CacheControl: 'no-store',
  }));
}

/** Admin-only, 60-second, single-object link that forces the right type and no caching. */
function signedViewUrl(key, { filename, contentType }) {
  return getSignedUrl(s3, new GetObjectCommand({
    Bucket: BUCKET,
    Key: key,
    ResponseContentType: contentType,
    ResponseContentDisposition: `inline; filename="${filename.replace(/[^\w.-]/g, '_')}"`,
    ResponseCacheControl: 'no-store',
  }), { expiresIn: SIGNED_URL_SECONDS });
}

const deleteDocument = (key) => s3.send(new DeleteObjectCommand({ Bucket: BUCKET, Key: key }));

module.exports = { objectKey, putDocument, signedViewUrl, deleteDocument };
```

### 6.3 Upload controller rules

- `multer.memoryStorage()` with `limits: { fileSize: 8 * 1024 * 1024, files: 10 }`, so nothing is written to Render's disk.
- Check the file's magic bytes (`%PDF-`, `FFD8FF`, PNG signature), reusing `hasImageSignature` from `uploadRoutes.js` and adding PDF.
- Reject PDFs containing `/JavaScript`, `/JS`, `/Launch`, `/EmbeddedFile` or `/Encrypt`.
- Re-encode JPEG and PNG with `sharp` (strips EXIF/GPS and neutralises polyglot files).
- Store `sha256`, size and type with the key in MongoDB. Never store a URL.
- Only applicants whose application is `DRAFT` or `CHANGES_REQUESTED` may upload; quota 30 files per hour.

### 6.4 Download controller: admins only, short-lived and audited

```js
// GET /api/admin/vendor-applications/:id/documents/:docId  (router already has protect + authorize('admin'))
router.get('/vendor-applications/:id/documents/:docId', asyncHandler(async (req, res) => {
  assertObjectId(req.params.id, 'application id');
  const application = await VendorApplication.findById(req.params.id);
  const doc = application?.documents.id(req.params.docId);             // must belong to THIS application
  if (!doc) throw ApiError.notFound('Document not found');

  await KybAccessLog.create({ adminId: req.user._id, applicationId: application._id, documentId: doc._id,
    action: 'VIEW', ip: req.ip, userAgent: req.get('user-agent')?.slice(0, 200) });

  const url = await kybStorage.signedViewUrl(doc.storageKey, { filename: doc.originalName, contentType: doc.mimeType });
  res.set('Cache-Control', 'no-store').json({ success: true, url, expiresInSeconds: 60 });
}));
```

**Why 60 seconds, and what it does not protect.** A presigned URL is a bearer token: anyone holding it during those 60 seconds can open the file. The protections are:
- a short lifetime;
- links issued only to authenticated admins;
- one link per view, with every view logged;
- `no-store` caching.

For stronger control, **stream the file through the API** instead (`GetObject` piped to the response with `Content-Security-Policy: sandbox`), so no URL ever exists outside the server. This is the proposal's recommended option; both work with R2.

**Frontend CSP:** with presigned URLs, add `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` to `frame-src` and `img-src` in `vercel.json`, for the admin viewer only. With streaming, add only `frame-src blob:`.

## 7. Residual risks and recommendations

1. **Contact details inside images.** A vendor can photograph a WhatsApp number. Recommended:
   - a "Report post" button that sends to an admin moderation queue (`contactFlags` already marks text masking);
   - optionally OCR on upload later (e.g. Tesseract or a cloud service).
2. **Uploads on Render's ephemeral disk.** Post photos are lost on redeploy. Move public images to an R2 *public* bucket, separate from the KYB bucket, when KYB storage is set up.
3. **Feed scaling.** `listFeed` reads all prequalified vendor ids on each request, which is fine for hundreds of vendors. At scale, add a `vendorEligible` flag to posts, maintained on verification changes.
4. **Token in localStorage.** Unchanged from the first audit; mitigated by the strict CSP. Moving to an HttpOnly cookie is the long-term fix.
